# 视频分镜提示词代码核查

核查时间：2026-10-30。读取当前代码、折槛图项目 v105 和数据库中的6条成功视频记录，仅进行了本地拼接对比，没有提交视频生成，也没有改动生成逻辑。

## 1. 最重要的结论

页面的「完整视频描述」绑定 `board.prompt`，但 `backend/video.py` 的 `video_prompt()` 没有读取这个字段。页面说明「这段描述与分镜内容共同用于动画生成」与实际实现不一致。

同样没有被拼入最终请求的字段还有：镜头景别 `framing`、运镜 `camera`、旁白 `narration`。因此修改这些字段无法直接改变模型看到的提示词。

本地对照实验：复制第一场分镜，只修改一个字段，然后重新调用 `video_prompt()` 比较字符串。结果如下：

| 单独修改的字段 | 最终提示词是否改变 |
| --- | --- |
| 完整视频描述 prompt | 否 |
| 景别 framing | 否 |
| 运镜 camera | 否 |
| 旁白 narration | 否 |
| 动作 action | 是 |

这不是通过观看视频得出的猜测，而是可复现的代码行为。

## 2. 数据怎样变成模型请求

1. `backend/workflow.py` 的分镜生成指令要求文本模型生成每场1–3镜，合计5秒，包含动作、对白、景别、运镜、音效及一段综合描述。此处调用 `vision.ask(..., [], fast=True)`，没有直接附上画作图片，而是使用文本上下文。
2. 用户在 `src/VideoStudio.vue` 编辑这些分镜字段，保存进项目。
3. 点击生成时，前端先保存项目，再确认当前场景，最后提交 `/videos`。
4. 后端 `video_prompt()` 从分镜重新拼接一段长提示词。
5. `payload()` 读取当前整幅原画，转换为PNG，以同一图片同时作为首帧和尾帧，提交给视频服务。

最终提示词的结构是：

```text
原有人像保持规则
+ 姿态、构图与背景保持的优先级规则
+ 固定全幅古画风格规则
+ 所有标注人物的姓名及中心点百分比
+ 当前场景标题
+ 按 duration 累加的时间段
  每段包含：可动作人物、action、对白姓名及文字、sound
+ 最终禁止事项与仅朗读指定对白的规则
```

这是同一段5秒视频里的时间描述，并不是分别生成两个镜头后剪辑。代码每段都强制写「固定全幅」，最后还禁止切镜与特写。

人物框没有作为区域控制、遮罩或带框参考图提交。传入的是无标注的整幅图片；框只转成「姓名＝横向X%、纵向Y%的原有人像」这类自然语言定位。人物中心坐标不能被视作服务端保证执行的区域约束。

当前实际参数：

```json
{
  "model": "wan3.0-video",
  "input": {
    "prompt": "后端重新拼接的长提示词",
    "media": [
      {"type": "first_frame", "url": "当前整幅画作的PNG数据"},
      {"type": "last_frame", "url": "与首帧相同的PNG数据"}
    ]
  },
  "parameters": {
    "resolution": "480P",
    "ratio": "adaptive",
    "duration": 5,
    "audio": true,
    "prompt_extend": false,
    "seed": 20261026
  }
}
```

没有单独的 `negative_prompt` 参数；禁止事项全部写在正向提示词里。时长、分辨率、音频、种子均硬编码，界面没有对应的实验选项。

## 3. 当前项目中已经能确认的矛盾

- 第一场完整视频描述仍写「2.5秒＋2.5秒」，但当前保存的 shots 已是「4秒＋1秒」。描述已经与结构化分镜脱节，而且前者不参与提交。
- 第一场动作包含带离、拖拽、挣扎、攀栏；系统提示同时要求所有人物双脚固定、禁止移位，并明确将拖拽降为原地袖口轻动。较大剧情动作在最终指令中被主动降级。
- 原图对应的张禹是站姿，但第一场动作里写「张禹端坐」；第五场要求原画端坐的皇帝立于殿侧、按住栏杆。这些与保持原始姿态的要求冲突。
- 当前第一场对白字符串长度为23（含标点），并非分镜生成指令建议的8字以内。后端只限制单条文本最多100字符，未强制落实总对白字数、单句规则和至少2秒发声时间。短时长内多动作加长对白会增加任务负担，此项影响程度需生成实验验证。
- 第二场第一个镜头 action 为空；第四场存在说话人ID为空的对白。按当前校验会阻止相应场景生成，需先补齐或删除无效字段。这些是输入有效性问题，不应归因于视频模型。
- 当前第一场编译后的提示词约1603字符，五场约1487–1603字符，其中很大部分是重复保持规则。长且重复的否定指令是否降低动作遵循，需要短提示词对照实验，不能仅凭长度直接认定。

## 4. 需要通过实验验证的因素

1. **首尾帧相同**：要求5秒后返回同一幅静态画，可能限制站起、移动、断栏等不可逆动作。保持其他输入不变，比较首帧单图与相同首尾帧；先确认服务接口支持对应输入形式。
2. **480P全幅下的小人物**：古画中人脸占整个画面很少，可能让嘴型、目光与身份细节难以辨认。比较分辨率；人物局部裁切只适合作为定位能力诊断，不代表产品应改成局部画面。
3. **同时安排的人物及动作过多**：第一场首镜允许8个人像动作，同时要求拖拽、攀栏、摆手、坐姿变化与说话。先用一个人、一处动作建立基线。
4. **音画联合任务**：当前始终 `audio=true`。比较无声微动作与加入一句短对白后的效果，判断问题主要来自画面还是声音及嘴型任务。
5. **自然语言人物定位**：比较人名定位、外观与位置定位。不能假定模型理解某个历史姓名就能稳定对应画中人物。

以上是代码与输入所提示的假设，本次没有重新生成或逐帧评估视频，因此不将它们写成已证实的模型故障。

## 5. 建议的测试顺序

每次只改变一个变量，保存完整实际请求、输入图片哈希、模型、分辨率、种子和输出，避免仅凭编辑器文本比较。

| 次序 | 对照内容 | 观察指标 |
| --- | --- | --- |
| 0 | 先修正编辑字段与实际请求不一致，并展示实际请求预览 | 编辑内容是否真正进入请求 |
| 1 | 同一画作、单一人物、单一微动作、无对白，固定全幅 | 是否动对人、有无增人、脸与服饰是否稳定 |
| 2 | 保留图片和动作，比较简短规则与当前长规则 | 动作能否看清、画风是否漂移 |
| 3 | 保留提示词，比较相同首尾帧与单首帧 | 动作幅度、结尾回弹、背景是否变形 |
| 4 | 保留其他参数，比较480P与服务支持的更高分辨率 | 人物面部和线条稳定性 |
| 5 | 在稳定的无声版本上增加一句短对白 | 发声人物、漏字、嘴型与画面稳定性 |
| 6 | 最后才加入第二个人或第二个时间段 | 是否出现动作串人或时间混乱 |

单动作基线的意图示例：

> 保持整幅古画构图与画风，固定机位。仅画面右侧端坐的人像（中心约横向77%、纵向47%）缓慢抬起右手少许，再放回原位。其余人物与背景静止。5秒，无对白，无字幕。

注意：把此文字只填进当前「完整视频描述」不会生效。测试前应接通该字段，或通过明确的实验请求传递这段提示词。若仍使用现有编译器，应先调整真正生效的 action、dialogue 等字段。

建议逐条记录四类结果：人物身份/构图保持、动作遵循、时序遵循、声音表现。只记录「好/不好」难以定位原因。

## 6. 旧记录和测试机制的注意事项

数据库里6条成功视频都使用旧画作，图片哈希为 `0e558649…`；当前新局部图哈希为 `4769ac84…`。旧记录来自项目v38、v39、v87、v90、v92，不能当作当前v105及新画的生成结果。最新一条的策略版本是 `original-figures-only-v2`，其余未保存策略版本。

本地6个视频额度槽目前均已占用，本次未重置。`test=true` 仍然走真实视频服务、同样的参数和额度，仅改变部分前置检查及任务标记，不是免费模拟。

任务会去重。同一输入再次提交会返回已存任务，不保证重新生成；seed、model、resolution等硬编码参数本身也没有直接加入任务去重键，因此实验功能应将完整生成配置纳入键或提供明确的新实验标识。

反过来，`board.prompt`、camera等字段虽然不影响实际视频提示词，却会改变分镜指纹，可能使同样的实际请求变成新的收费任务。这尤其容易造成「修改描述后再试，效果没变」的误判。
