# 画作资料库

存储可选择 Docker MySQL 或兼容 SQLite，当前选择由 `.env.mysql` 中的 `CREATION_DB_BACKEND` 决定。原 SQLite 文件是 `data/projects.sqlite`。升级前本地备份是 `data/backups/before-catalog-upgrade.sqlite`，备份不提交版本库。

## 页面

画作探索 → 画作资料库，按作品档案、人物档案、人物关系、历史事件、史料来源、背景原文组织。作品年代和故事年代分开记录。人物关系通过“从史料分析关系”显式提取；建议以虚线展示并标为待核对，确认或编辑后转为人工关系。时间线保持录入顺序，不猜测年份或补造事件。

旧人物和来源直接展示。未填写的作品字段和事件留空，关系在用户点击运行后分析，原始笔记完整保留。“编辑”打开独立草稿，“取消”丢弃草稿，“保存到资料库”才提交；刷新重新读取已保存记录。修改人物、来源或背景时沿用现有审核失效逻辑。

关系及事件可以关联人物和来源，并保存原文引文及来源版本。存在引文表示可追溯，不表示独立核实了史实。修改来源后旧引文保留并显示待复核。后台拒绝不存在的人物和来源、新填的伪造引文、自关系及重复编号。不同项目按 project_id 隔离。

## 存储

项目快照 `projects.body` 是唯一权威数据。每次保存时，在同一个数据库事务里更新项目版本、事件日志与以下可查询的结构化表；这些表是查询投影，不是另一套独立资料：

| 表 | 内容 |
| --- | --- |
| artwork_catalog | 作品名称、档案字段 |
| artwork_people | 人物编号、姓名、人物详情 |
| artwork_sources | 来源编号、标题、版本、原文 |
| artwork_relations | 关系编号、起点、终点、关系及证据 |
| artwork_events | 事件编号、名称、时间说明、顺序、人物及证据 |

使用参数化 SQL。后端在保存之前检查版本；冲突返回 409，不覆盖数据库。应用启动会从旧项目重建查询表，不改变原始资料或项目版本。请通过应用编辑，直接改查询投影会被下一次项目保存覆盖。

`GET /api/projects/{id}/catalog` 提供当前画作的统一结构化读取；写入沿用带版本的 `PUT /api/projects/{id}`。作品字段位于 `paintingInfo`，关系位于 `personRelations`，事件位于 `historicalEvents`。前端不会直连数据库。

## MySQL 部署

已提供 MySQL 8.4 Docker Compose、连接池、InnoDB 事务与迁移工具。实际连接类型可通过 `/api/database/status` 及资料库顶部标识查看。部署和迁移详见 [MySQL 说明](MYSQL.md)。

本地前端固定为 5173，代理固定指向后端 8002；端口占用时报错，不自动切换。

## 验证

`npm run build`；`.venv/Scripts/python.exe -m pytest -q`。新增测试验证数据库重连读取、查询表同步、冲突不覆盖、无效关联拒绝、来源变更后的旧引用状态及项目隔离。
